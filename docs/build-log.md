# Build log

What has been built, why, what it cost, and what is still open.

Companion to [architecture.md](architecture.md) (the design) and [adr/](adr/) (the
load-bearing decisions). This file is the narrative: the order things happened in, the
mistakes made along the way, and the state of play.

**Status at time of writing:** Phases 0–4 complete. Phase 5 (hardening) not started.
8 commits · 67 tests passing · lint, contract drift, typecheck, test and build all green.

---

## 1. Where this started

An empty directory. No git history, no package manifest, nothing.

Four decisions were settled before any code was written, because each is expensive to
reverse:

| Decision | Choice |
| --- | --- |
| Commerce backend | Custom internal REST API, described by OpenAPI |
| Framework | Next.js App Router (React Server Components) |
| Cart ownership | Backend-owned, server-authoritative |
| Auth | Session cookie issued by the internal API |
| Payments | Hosted redirect (no card data on this origin) |
| Styling | Tailwind v4 + shadcn/ui, Radix base |

Three were written up as ADRs because they are the ones that would be argued about later:
[BFF topology](adr/0001-nextjs-as-bff.md),
[server-authoritative cart](adr/0002-server-authoritative-cart.md),
[selective runtime validation](adr/0003-selective-runtime-validation.md).

## 3. What was built, commit by commit

### `9ec7e40` — Architecture and agent configuration
Design docs and three ADRs. Also encoded the same invariants as **five agent skills**
(`commerce-data-layer`, `cart-mutations`, `commerce-caching`, `checkout-flow`,
`rsc-boundaries`) and **three review subagents** (`commerce-reviewer`,
`api-contract-auditor`, `perf-budget-auditor`), so the rules are applied at authoring time
instead of discovered in review. `AGENTS.md` kept deliberately short — always-on rules
dilute attention, so it holds only the invariants that cause security bugs or wrong charges
and routes everything else to skills.

### `b3d5fe4` — Scaffold
Next 16.3.4, React 19.2.8, Tailwind v4, shadcn/ui on the Radix base, TypeScript strict,
App Router, `src/`.

The point of this phase was making the architecture **executable rather than advisory**:

- ESLint blocks `src/components/**` importing `src/commerce/**`, scoped to the `@/commerce`
  alias so the legitimate `src/components/commerce/` directory is not caught. Proven with a
  red/green fixture, then the fixture was deleted.
- CI runs lint, typecheck, build, and Lighthouse budget assertions.

### `e8c4989` — Commerce data layer
A typed data layer that works with **no backend at all**.

- `openapi/commerce.yaml` — a provisional spec drafted by the frontend. It is a *proposal to
  the backend team*, not a description of a shipped service. It encodes the three primitives
  the storefront cannot work around: idempotency keys, machine-readable error codes, and
  money as integer minor units.
- Types generated by `openapi-typescript` and committed; CI fails on drift.
- `money.ts` — integer minor units throughout. The only float conversion is inside
  `formatMoney`, immediately before rendering. Multiplication rejects fractional multipliers
  because those need a rounding policy the storefront must not invent. Tested against JPY
  (0 decimals) and KWD (3), which a hardcoded `/100` gets wrong.
- `errors.ts` — every backend failure normalised into a domain union. Dispatch is on the
  machine-readable `code`, never on prose.
- MSW handlers seeded from the same fixtures, with `onUnhandledRequest: "error"`.

### `788c73f` — Catalog (PLP + PDP)
Enabled Cache Components. The PDP shell is cached and served as static HTML while price and
stock stream at request time — the build reports `/products/[slug]` as **Partial
Prerender**, and a single response contains both the `Loading price` fallback and the
streamed price.

Stale pricing is now *structurally* impossible rather than a matter of tuning TTLs, because
the price is not in the cached payload at all.

### `95fa2c1` — Delivery pipeline gates
Review of the Docker/Jenkins delivery setup. Three ways it could have put a broken build in
front of customers, all fixed. See §5.

### `4d95c8e` — Cart Server Actions
Server Actions are the only code that mutates the cart or touches the cookie. Cart creation
happens on first write, never during render, because cookies cannot be set while rendering.

### `ee147bb` — Local development without the backend
`pnpm dev` pointed at a placeholder host and died. See §6.

### `be5524e` — Checkout and hosted payment redirect
Full funnel closed. The return handler treats every query parameter as attacker-controlled.
See §4.

## 4. The decisions worth remembering

**Two API clients, not one.** Catalog uses a session-free client; cart and checkout use a
session-forwarding one. Not stylistic: catalog responses are cached and shared across every
visitor, so a session travelling with them risks serving one shopper another's response —
and cookies cannot be read inside a `use cache` scope anyway.

**Idempotency keys are scoped by cart version.** Keying on
`(operation, cartId, variantId, quantity)` cannot distinguish an accidental retry from a
customer genuinely adding a second copy of the same item; it silently swallows the second.
The version increments on every mutation, so a retry carries the same version and collapses,
while a real repeat gets a new key. For checkout it is cart id + cart version, so a
double-clicked Pay cannot create two orders.

**The first cart is seeded by a stable client id.** `createCart` has no cart version to key
against, so the client sends a `useId()` value that is stable for the life of the button. A
double-clicked *first* add cannot create two carts. A fresh random value per click would be
the exact anti-pattern idempotency exists to prevent.

**Optimistic values are display-only.** Counts may be optimistic; anything a customer could
read as the amount payable comes from the server.

**The debounce lives inside the transition.** `useOptimistic` only holds while a transition
is pending, so sleeping outside it would snap the number back before the request was even
sent. Only the final click writes, and it sends an absolute quantity, never a delta.

**Server Actions reach client components as props.** Components must not import the data
layer; threading a prop is cheaper than weakening that boundary. They receive machine-readable
status unions (`CartFeedback`, `CheckoutFormState`), never backend prose.

**The return URL is never trusted.** Verified by attacking the running app:

| Request | Result |
| --- | --- |
| `?ref=X&status=success&amount=1`, order unsettled | → `/checkout/confirming` (not the order page) |
| `?ref=X`, genuinely settled | → `/orders/X` |
| no `ref` | → `/cart` |
| `?ref=ord_attacker&status=success` | → `/checkout/confirming`, asserts nothing |

**Pending is a real state.** The confirming screen polls with backoff (1s → 8s, ~60s cap)
and then hands off to support quoting the reference. Asserting failure early causes
duplicate payments; asserting success causes unpaid orders.

## 5. Delivery pipeline

Docker image (Node 22, standalone output, non-root, ~298 MB) plus a Jenkins pipeline that
builds, pushes an immutable SHA-tagged image, and runs `deploy/deploy.sh` over SSH with
automatic rollback. Correctness gates stay in GitHub Actions.

Verified by actually building and running the image: `output: 'standalone'` does work with
Turbopack and `cacheComponents`; the container runs as uid 1000 with no `node_modules` in
the runtime stage; PLP and PDP serve with PPR intact; the revalidation endpoint returns
401/401/200 for missing/wrong/correct secrets.

Three real bugs found and fixed in review:

1. **No branch guard** — any branch triggering the job deployed over production.
2. **Mock-API images were deployable** — the parameter description warned they bake fixture
   products into the prerendered catalogue, but a warning is not a control.
3. **The smoke test proved nothing** — it requested `/`, which is prerendered into the image
   and returns 200 even with the commerce API completely unreachable. It now requests a PDP
   and asserts availability rendered, because the streamed offer is the only part that needs
   a live backend.

A fourth was caught later: the Dockerfile did not copy `public/`, which would have 404'd
every static asset once that directory existed.

## 6. Mistakes made, and what they cost

Recorded because the reasoning is more useful than a clean story.

**The 120 kB JS budget was never achievable.** Set in Phase 0 before anything existed.
Measured on the production build, `/` — a route with *zero* client components — already
ships **131 kB** of React 19 + Next 16 runtime. Re-baselined to 170 kB with the measured
breakdown in the architecture doc. App-owned JS is only +5 to +21 kB per route.

**A JS measurement was wrong by 5×.** The first reading was 827 kB. My `next start` had
failed with `EADDRINUSE` and I was silently measuring a `next dev` server, which ships
devtools and HMR. Also: `<script noModule>` (~39 kB legacy polyfill) must be excluded, or
every route is overstated by a third.

**`revalidateTag('cart:...')` was specified but meaningless.** The cart is never cached, so
there is no tag to expire. Invoking a Server Action already re-renders the route. Removed
from the doc rather than implemented.

**The error taxonomy had no `not_found`.** A deleted product normalised to `Unavailable`, a
server fault — making every removed product look like an outage and burying real outages
among them.

**The spec contradicted the implementation.** The spec says the error `message` must never be
shown to customers; `normalizeError` was putting it straight into `ValidationFailed` for the
UI to render. Caught by the `commerce-reviewer` subagent. Now exposes a machine-readable
`field` plus a quarantined `devMessage`.

**Per-line prices were unvalidated.** Only cart totals were checked. The backend computes
totals independently, so a corrupt `unitPrice` can hide behind a clean total — and that line
is what the customer reads. `cartLineMoneySchema` existed but was never wired up, which is
worse than absent: false assurance.

**`params`/`searchParams` awaited outside Suspense — twice.** Once on the PDP (Phase 2) and
again on `/checkout` (Phase 4). Both blocked the route from prerendering. Worth encoding in
the `rsc-boundaries` skill.

**`git add -A` swept the user's in-flight work into my commit.** The Dockerfile, Jenkinsfile,
`deploy.sh` and `.dockerignore` landed inside `788c73f` with my commit message, misattributing
authorship. Subsequent commits stage explicit paths.

**Fixture images pointed at a host that does not resolve**, so `/_next/image` returned 500 for
every product image. Replaced with local PNGs — *not* SVG, because Next refuses to optimise
SVG unless `dangerouslyAllowSVG` is set, and enabling that for CDN-sourced product imagery
accepts script-bearing SVG. Not a flag worth setting to make placeholders render.

## 7. Verification

```bash
pnpm lint && pnpm codegen:check && pnpm typecheck && pnpm test && pnpm build:ci
```

- `pnpm dev:mock` — dev server against the mock API (use this, not `pnpm dev`, until the
  backend exists)
- `pnpm typecheck` runs `next typegen` first: route types are generated, so a bare `tsc`
  fails on a clean checkout
- `pnpm codegen:check` fails if the committed types drift from the spec
- `build:ci` builds against `scripts/mock-api.mjs`, because `use cache` content is
  prerendered and the build performs real catalog requests

67 tests, weighted by risk rather than pyramid orthodoxy: money arithmetic, error
normalisation, idempotency key derivation, cart actions including cookie and cart-creation
behaviour, catalog caching and tagging, and checkout including order-state validation.

## 8. Still open

**Blocking a production launch:**

1. **The OpenAPI spec is ours, not the backend team's.** Everything is built against a
   contract the frontend invented. The §9 asks in the architecture doc — idempotency keys,
   the cache-invalidation webhook, structured error codes, cart merge semantics — remain
   unconfirmed by anyone on the backend side.
2. **Phase 5 has not started**: axe accessibility sweep, OpenTelemetry with trace propagation,
   frontend RUM, load testing, and the Playwright E2E suite.
3. **Node 20 is EOL locally** (2026-04-30). CI and the Docker image run Node 22.
4. **Jenkins placeholders** — `registry.example.com`, `your-server.hetzner.example`.

**Known limitations, deliberate:**

- **Soft 404 on missing products.** The prerendered shell commits HTTP 200 before streaming,
  so a deleted product renders 404 UI but returns 200. The route is `noindex`. A hard 404
  requires resolving existence before streaming, which costs the static shell.
- **`revalidateTag` is per-container.** Fine on one host; with two replicas a publish webhook
  only invalidates whichever replica receives it.
- **Nothing gates Jenkins on GitHub Actions passing.** Two CI systems, no handshake — Jenkins
  will happily deploy a commit that failed CI.
- **`scripts/mock-api.mjs` and `with-mock-api.mjs` are scaffolding.** Delete both, and switch
  CI back to plain `pnpm build`, once the real API is reachable.
- **Cart merge on login is unimplemented** — the endpoint is specified, the flow is not built.
- **No `public/` favicon or real product imagery**; placeholders only.
